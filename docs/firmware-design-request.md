Bluetooth Ohmmeter Firmware

Objective: Implement embedded C firmware for an ohmmeter that measures resistance with the MIKROE Multimeter Click and transmits readings through a Microchip RNBD350 Bluetooth Low Energy module. Integrate the work into the existing MPLAB Code Configurator (MCC) project. Reuse the generated GPIO, timer, UART, and SPI drivers; do not replace or regenerate them unless a verified project requirement makes that unavoidable.

Hardware and Timing
•	SERCOM0: RNBD350 command/response interface and transparent data pipe. Use the MCC-generated interface and configured parameters. The documented RNBD350 default is 115200 baud, 8 data bits, no parity, one stop bit, and no flow control; report any project mismatch before proposing a change.
•	SERCOM2: Dedicated diagnostic UART. Route development and runtime diagnostics only to this port. Never mix diagnostics with RNBD350 commands or meter data on SERCOM0.
•	SERCOM5: SPI interface to the Multimeter Click MCP3204 ADC. Use the MCC-generated SPI interface and existing chip-select GPIO.
•	Resistance measurement range: Configure the Multimeter Click for a measurement range of 0 Ω to 10 kΩ. During initialization, set RES_A, RES_B, and RES_C to the documented logic values required to select this range, as defined by the authoritative range-control truth table. Verify and report the selected value for each signal before implementation; do not infer or invent the GPIO combination. Express the three settings through named constants or an enum and keep the range fixed during normal operation.
•	TC0: Use the existing MCC-generated TC0 configuration to produce a periodic 100 ms event. If it is not already configured for that interval, first report the clock source, prescaler, period, callback API, and calculated event interval. The callback or ISR may only set a flag or increment a bounded pending-sample counter; perform all SPI access, conversion, formatting, UART transmission, and diagnostics in foreground code.
•	Status LED: Toggle every 1,000 ms while Bluetooth is disconnected and every 200 ms while connected and actively sending data. Use non-blocking scheduling without delay-based timing.
Required Behavior
1.	Initialization: Initialize application state, fixed range GPIO, SERCOM0 receive handling, SERCOM5 access, TC0, and the LED scheduler through existing MCC entry points. Configure or verify the RNBD350 only with documented commands and responses. Commands are ASCII terminated by carriage return; do not issue another command until the prior response is complete.
2.	RNBD350 receive path: Continuously collect SERCOM0 bytes in a bounded buffer or ring buffer. Parse complete responses and unsolicited events across arbitrary fragment boundaries. Tolerate CR/LF delimiters and prompts, preserve partial messages, reject overlength input safely, and expose explicit connection and transparent-data-ready states. Never infer connection from elapsed time or successful writes.
3.	STREAM OPEN transmission prerequisite: Do not send any application data through BLE until the RNBD350 receive parser has received and recognized the documented STREAM OPEN status. A Bluetooth connection indication alone is not permission to transmit. Set the transparent-data-ready state only after STREAM OPEN is received; clear it immediately on disconnect, stream-closed status, reset, timeout, or any event that invalidates the transparent data channel. Measurements may continue while waiting, but discard unsent readings so that no backlog is transmitted when the stream opens.
4.	Measurement scheduling: Request one resistance measurement every 100 ms. If foreground processing has not completed the previous request, retain at most one pending request and record an overrun diagnostic; do not accumulate stale samples.
5.	Measurement conversion: Read the documented MCP3204 single-ended resistance channel and convert the 12-bit result with the documented 0–10 kΩ equation and calibration assumptions. Represent valid resistance as a non-negative integer number of ohms. Define explicit behavior for SPI failure, conversion failure, saturation, open circuit, and out-of-range results; never transmit fabricated values.
6.	Transmission gate: Send a reading only when the parsed Bluetooth state is connected and the documented transparent data channel is ready. Treat these as separate states when the user guide distinguishes them. Never send meter data while disconnected or in command mode. After a disconnect event, stop immediately and discard unsent readings so that reconnection cannot release a stale backlog.
7.	JSON message format: Define the meter message contract only here and reference this requirement everywhere else. Each transmitted record must be exactly {"Meter":{"ohm":10000}}\r\n, replacing only 10000 with the measured non-negative integer resistance. Encode as UTF-8 and append exactly one carriage return byte (0x0D) and one line feed byte (0x0A). Add no units, timestamps, comments, prompts, null bytes, additional spaces, or framing. Implement formatting in one dedicated function or module using a bounded operation such as snprintf, and verify that the complete record fits the transmit buffer.
8.	Concurrency: Keep interrupt work minimal, protect shared ISR/foreground state, avoid blocking waits in the main service loop, and prevent UART receive loss during SPI, formatting, transmission, or diagnostic processing.
Software Structure
•	Separate the application into clear responsibilities, for example: rnbd350.c/.h, ohmmeter.c/.h, app.c/.h, and dedicated diagnostic files diag.c and diag.h, while following the existing repository conventions. All diagnostic implementation and public diagnostic interfaces must reside in diag.c and diag.h, respectively.
•	Use a small explicit state machine for RNBD350 initialization, command waiting, disconnected, and connected/data-ready states.
•	Provide interfaces for RNBD350 byte ingestion and service processing, connection-state query, resistance acquisition/conversion, 100 ms sample scheduling, and LED scheduling.
•	Keep board-specific MCC symbol names in a thin adaptation layer where practical. Search the generated project for the actual SERCOM0, SERCOM5, TC0, chip-select, RES_A/B/C, and LED API names before writing calls.
•	Add concise comments for protocol state transitions, ADC conversion assumptions, and range selection. Avoid unnecessary abstraction and dynamic memory allocation.
Implementation Constraints
•	Use portable embedded C consistent with the existing compiler and repository style.
•	Do not regenerate, replace, or directly edit MCC-generated source unless the verified project architecture requires it. Keep application logic in user-maintained files.
•	Do not add an RTOS, heap allocation, blocking delays, or unrelated features.
•	Use fixed-size buffers, compile-time constants, defensive bounds checking, and deterministic behavior.
•	If a required symbol, clock rate, pin mapping, ADC channel, RNBD350 configuration choice, event string, conversion constant, or authoritative hardware detail cannot be verified from the repository or listed references, do not implement the affected behavior. Record it under Open Questions, identify what was checked, and state what information is required to proceed.
Diagnostics
•	Implement a small diagnostic module or wrapper for SERCOM2 with severity levels such as DEBUG, INFO, WARN, and ERROR. Allow verbose output to be enabled or reduced at compile time without changing application logic.
•	Emit concise but sufficiently detailed CRLF-terminated text messages for firmware startup, initialized peripherals, configured resistance range, RNBD350 command transmission, parsed RNBD350 responses and unsolicited events, Bluetooth state transitions, ADC raw values, calculated resistance, JSON transmission success or failure, buffer overflow, parse error, timeout, SPI failure, invalid or out-of-range measurement, and recovery action.
•	Prefix each message with a monotonic timestamp in milliseconds derived from an existing system tick or timer, the severity, and a subsystem tag; for example: [001250 ms][INFO][BLE] Connected. Do not add a second timer solely for timestamps.
•	Do not log from an ISR and do not block time-critical sampling or Bluetooth receive processing. Queue or defer diagnostics to foreground code, use fixed-size buffers, and define safe behavior when the diagnostic port is busy or its queue is full.
•	Diagnostic text must never be transmitted over SERCOM0 and must not alter the exact Bluetooth JSON payload. Avoid exposing uninitialized memory or printing binary buffers as strings.
•	During normal connected operation, provide enough information to correlate each 100 ms measurement with its raw ADC result, converted ohm value, and transmission result. If this volume affects timing, support a compile-time verbose-measurement option while always retaining state changes, warnings, and errors.
Acceptance Criteria
•	At power-up while disconnected, the LED toggles every 1 second and no meter record is written to SERCOM0.
•	A documented RNBD350 connection indication establishes connected state without resetting the MCU; data transmission begins only after transparent-data readiness is also confirmed.
•	While connected and data-ready, one valid record conforming to the canonical JSON wire format is sent for each successfully serviced 100 ms sample request, and the LED toggles every 200 ms.
•	A documented disconnect indication immediately prevents later meter transmissions, discards unsent readings, and restores the 1-second LED interval.
•	The parser recognizes connection and disconnect messages when delivered one byte at a time, in fragments, or adjacent to other complete RNBD350 responses.
•	Every transmitted meter record matches the canonical JSON wire-format requirement byte for byte; no second payload template or independently maintained format definition exists in the code.
•	Representative measurements near 0 Ω and 10 kΩ follow the documented conversion, calibration assumptions, and declared invalid-measurement handling.
•	SERCOM2 reports startup, peripheral initialization, Bluetooth transitions, measurements, transmissions, warnings, and errors with timestamp, severity, and subsystem context.
•	Diagnostic stress does not corrupt SERCOM0 traffic, delay the 100 ms schedule, block receive parsing, or introduce unbounded memory use.
•	The project builds without warnings introduced by the new application code and without unnecessary changes to generated drivers.
